1. Overview: What Changed & Why

The Go-Browse framework's Explore flow has been upgraded to produce semantic trajectories — trajectories where every action carries rich natural language descriptions, the task intent evolves as the agent learns more about the page, elements are visually grounded via Set-of-Mark, and post-hoc verification classifies task types with detailed reasoning.

The upgrade was driven by analysis of Explorer (ACL 2025), which demonstrated that semantically rich trajectories produce better training data for multimodal web agents. The implementation bridges the gap between Go-Browse's multi-node graph exploration and Explorer's deep single-site semantic trajectory synthesis.

Key Insight: The original Go-Browse produced "raw" trajectories — just action strings and observations. The upgraded pipeline produces self-describing trajectories where every step documents what was done (natural language), why (reasoning), where (bounding box + URL), and what the agent now understands the task to be (refined goal). This makes the data directly usable for training vision-language-action models.

Stuck detection Basic action repetition Multi-level: action+error loop detection + hard stuck detection
URL tracking Not per-step page_url_before + page_url_after per step

3. Phase 0: CAPTCHA Detection NEW

webexp/agents/captcha_detection_agent.py CaptchaDetectionAgent

Purpose

Before exploring any node, the framework checks whether the page is a CAPTCHA challenge. If detected, the node is skipped entirely — saving LLM calls that would otherwise be wasted on unsolvable pages. Uses GPT-4V for visual inspection with a simple yes/no prompt.

Input
  • screenshot — PIL Image or numpy array of the page
Output
  • bool — True if CAPTCHA detected, False otherwise
  • On error: returns False (fail-open — don't skip valid pages)
Integration in web_explore.py (lines 523-530)
# Before exploring each node:
obs = get_fresh_obs(env)
if "screenshot" in obs and captcha_detector.is_captcha(obs["screenshot"]):
    logger.warning(f"CAPTCHA detected at {curr_node.url}, skipping node.")
    graph.add_to_explored(curr_node)
    exploration_count += 1
    curr_node = graph.get_next_node()
    continue

4. Phase 1: Enhanced Task Proposal ENHANCED

PageExplorerAgent & NavExplorerAgent — Improved Task Quality

What Changed

The goal_str for both explorer agents was rewritten to enforce higher-quality task proposals. The LLM is now instructed to produce tasks in a standard format with concrete constraints.

Task Format Requirement

"<action verb> <specific details with constraints> on <website>"

Examples Given to LLM

GoodBad
"Find a 4K OLED TV under $1000 with free shipping on BestBuy""Look at TVs"
"Book a hair appointment for Saturday morning on Yelp""Find a salon"
"Add iPhone 15 Pro 256GB to cart on Amazon""Shop for phones"

Task Tags

Each task is tagged: [INFO] information seeking, [NAV] navigation, [MOD] content modification. Multiple tags supported (e.g. [INFO][MOD]).

SoM Integration

When use_som=True is configured, the prompt builder includes Set-of-Mark instructions in the system message so explorer agents understand numbered element tags.

5. Phase 2: Feasibility Check

Structurally unchanged. Each proposed task is attempted by a SolverAgent. If the evaluator marks it as success, the task is deemed "feasible." The enriched evaluation (see Phase 4) applies during this step, providing task type classification and failure reasons for infeasible tasks.

6. Phase 3: Semantic Trajectory Generation CORE NEW

This is the heart of the upgrade. Every solver trajectory step now carries rich semantic metadata. Below is a breakdown of each new capability.

6.1 Set-of-Mark Visual Grounding NEW

webexp/explore/grounding/set_of_mark.py webexp/explore/grounding/som_processor.py Set-of-Mark Grounding

How It Works
  1. som_processor.py walks BrowserGym's accessibility tree, extracts bounding boxes from extra_element_properties, and builds a Region-of-Interest dict mapping bid → {rects, tag, text}.
  2. set_of_mark.py draws semi-transparent colored rectangles with numbered labels over each interactive element on the screenshot. Color is deterministic per element ID.
  3. The annotated screenshot replaces the original in the observation, while the original is preserved at obs["som_screenshot_original"].
  4. A som_id_info dict maps SoM tag IDs (which are BrowserGym bids) → {bbox, tag, text} for downstream action grounding.
Input
  • BrowserGym observation: screenshot + axtree_object + extra_element_properties
Output
  • obs["screenshot"] → SoM-annotated image
  • obs["som_screenshot_original"] → original screenshot
  • obs["som_id_info"] → bid-to-bbox mapping
  • obs["som_visible_ids"] → elements visible on screen
  • obs["som_above_ids"] → elements above viewport
  • obs["som_below_ids"] → elements below viewport
Integration in SolverAgent.obs_preprocessor() (lines 298-305)
if self.use_som:
    try:
        processed = process_observation(processed)
        # Screenshot is now the SoM-annotated version
    except Exception as e:
        logger.warning(f"SoM processing failed: {e}")

When use_som=True, the prompt builder includes SoM instructions explaining that numbered tags correspond to interactive elements and can be referenced in actions.

6.2 Evolving Task Refinement NEW

refined_goal — Task Description Evolves Each Step

How It Works
  1. LLM is prompted to output a refined_goal field in its JSON response — the agent's updated understanding of what it's trying to accomplish.
  2. SolverAgent parses refined_goal from the LLM response and stores it in self._refined_goal (line 386).
  3. Episode runner injects refined_goal into callback_context_seed (episode.py line 242), making it available to subsequent steps.
  4. Prompt builder renders the current refined goal as a # Current Task Understanding (evolving) section in the prompt — the LLM sees its own evolving understanding.

Example Evolution

Steprefined_goal
0 (initial)"Find a product on Amazon"
3"Find a coffee maker under $100 with 4+ stars and free shipping on Amazon"
6"Purchase the Keurig K-Mini coffee maker ($79.99, 4.5 stars) on Amazon"
Prompt Builder — refined_goal_message() (lines 392-401)
def refined_goal_message(self, refined_goal: str | None) -> str:
    if not refined_goal:
        return ""
    return (
        "# Current Task Understanding (evolving)\n"
        "The task you are trying to accomplish has been refined based on "
        "what you've learned so far. Your current understanding is:\n\n"
        f"{refined_goal}\n\n"
        "Update this description as you learn more specific details "
        "(e.g., exact product names, prices, constraints)."
    )

6.3 Natural Language Action Descriptions NEW

action_in_natural_language — Dual Action Representation

How It Works

The LLM is now required to output action_in_natural_language alongside the raw action. This gives every step two representations of the same action:

  • Grounded form: click('bid_42') — executable by BrowserGym
  • Natural language: "Click on the 'Sony WH-1000XM5 Wireless Headphones' link in the search results" — human-readable, used by downstream agents
LLM Output Format (from solver_prompt_builder.py)
{
  "thought": "I need to click on the first search result...",
  "action": "click('bid_42')",
  "action_in_natural_language": "Click on the 'Sony WH-1000XM5' product link",
  "refined_goal": "Find Sony WH-1000XM5 headphones under $350 on Amazon"
}
Consumers of action_nl
  • Evaluator: Uses action_nl as the primary action description (falls back to raw action)
  • TaskSummarizationAgent: Builds action list from action_nl preferentially
  • Logging: Both raw action and NL description are logged for debugging

6.4 Element Metadata Extraction NEW

_extract_element_metadata() — Parse Element Info from Axtree

How It Works (solver_agent.py lines 154-185)

After the LLM selects an action targeting bid_XX, the agent parses the accessibility tree to find the element and extract its properties: 

{
  "bid": "42",
  "tag": "link",
  "text": "Sony WH-1000XM5 Wireless Noise Canceling Headphones - $348.00"
}

This bridges the gap between the abstract bid reference and the actual page element, providing rich context for training and analysis.

6.5 Per-Step URL Tracking NEW

page_url_before & page_url_after

How It Works
  • page_url_before: Captured from obs["open_pages_urls"][0] before the action is executed (solver_agent.py line 345).
  • page_url_after: Written to the last trajectory step after env.step() completes (episode.py lines 233-237).

This enables precise tracking of navigation effects — did the action cause a page change? Useful for filtering navigation vs. in-page actions during training data preparation.

6.6 Enhanced Stuck Detection ENHANCED

Multi-Level Stuck & Retry-Loop Detection

Three Levels of Detection (solver_agent.py lines 391-429)
LevelConditionAction
1. Retry-loop Same (action, error) pair ≥3 consecutive times Raises ValueError → episode ends, forces replan
2. Soft stuck ≤2 unique actions in last 5 steps (≥4 steps history) Logs warning, continues (prompt builder may inject recovery advice)
3. Hard stuck Same action executed ≥6 consecutive times (with or without errors) Raises ValueError → episode ends, prevents infinite loop
Error Recovery in Prompt Builder (solver_prompt_builder.py lines 204-338)

New methods classify errors and inject targeted recovery advice into the prompt:

  • _classify_error() — categorizes: multi_action, timeout, element_not_found, navigation_error, etc.
  • _error_recovery_advice() — returns specific guidance per error category
  • strategy_change_message() — escalated warning when same action+error repeats
  • silent_stuck_message() — warns when same action repeats without errors

7. Phase 4: Enhanced Evaluation ENHANCED

webexp/explore/core/evaluator.py Evaluator — Task Type Classification

What Changed

The evaluator now classifies trajectories into four task types with detailed reasoning, instead of just returning binary success/failure.

Task Types

TypeDefinitionSuccess Criteria
transaction Booking, ordering, add-to-cart, checkout Agent reaches checkout/login page or initiates transaction
information_seeking Finding product info, reviews, comparisons, maps Agent's response contains the requested info or states unavailability
site_navigation Navigating to a specific page Final page matches the navigation target (ignores agent's text response)
content_modification Modifying page content or configuration Final page state shows the modification was applied (ignores agent's text response)

Output Format

Thoughts: <your thoughts and reasoning process>
Task Type: <transaction|information_seeking|site_navigation|content_modification>
Status: <"success" or "failure">
Failure Reason: <if status is failure, briefly explain why. If success, write "N/A">

Stored in Trajectory

trajectory.misc["evaluation_info"] = {
    "output": {"thoughts": ..., "task_type": ..., "status": ..., "failure_reason": ...},
    "task_type": "information_seeking",
    "failure_reason": "Agent could not find the requested product",
    "reward": 0.0,
    "model_usage": {"prompt_tokens": 1500, "completion_tokens": 100, "total_tokens": 1600}
}

8. Phase 5: Task Summarization NEW

webexp/agents/task_summarization_agent.py TaskSummarizationAgent

Purpose

After all trajectories for a node are collected, _summarize_node_trajectories() iterates over every feasible task's positive and negative trajectories and calls TaskSummarizationAgent to produce a clean, coherent task description from the full action history and screenshots.

This is a critical addition because the original task proposal may be vague or inaccurate. The summarized goal captures what was actually accomplished, not what was initially proposed.

Input
  • Action history (preferring action_nl, falling back to raw action)
  • Up to 8 evenly-sampled screenshots from the trajectory
  • Original task proposal for context
Output
  • Clean task description: "<action verb> <details> on <website>"
  • Stored in trajectory.misc["summarized_goal"]
  • Persisted via trajectory.save_info() (no re-saving screenshots)
  • Skips if already summarized (idempotent)
Integration in web_explore.py (line 600)
# After all solvers complete for the node:
_summarize_node_trajectories(curr_node, evaluator.model_name)
Summarization Prompt Requirements
  1. Task must contain an action verb (Buy, Book, Find, Check, Search, etc.)
  2. Task must be clear, specific, and provide all necessary info
  3. Task must end with "... on <website_name>"
  4. Task must include constraints (budget, features, specs)
  5. No quotation marks in the task description

Key Architectural Decision: The semantic fields flow through three layers: (1) LLM outputs them in JSON → (2) SolverAgent parses and enriches them → (3) Episode runner records them in TrajectoryStep and propagates refined_goal forward. This separation keeps the agent stateless per-step while the episode runner manages cross-step state.

13. Configuration — Enabling Semantic Features

All new features are opt-in via the YAML config. Example:

# In configs/go_browse_config.yaml

solvers:
  - agent_factory_args:
      name: SolverAgent
      model_id: gpt-4o
      use_som: true          # ← Enable Set-of-Mark visual grounding

evaluator:
  model_name: gpt-4o         # Used by Evaluator, TaskSummarizationAgent, CaptchaDetectionAgent
Token cost impact: The additional JSON fields (action_in_natural_language, refined_goal) increase completion tokens by ~2-3x. Task summarization adds 1 extra GPT-4V call per trajectory. CAPTCHA detection adds 1 cheap call per node (10 token max). SoM processing is CPU-only (no API cost) but adds ~100-200ms per step for image overlay.
