1. Tổng Quan Kiến Trúc

Go-Browse là một framework Python dùng để thu thập dữ liệu huấn luyện không giám sát cho web agent. Ý tưởng cốt lõi: cho một LLM-agent tự động duyệt qua một website, đề xuất các nhiệm vụ (task) khả thi, kiểm tra tính khả thi, rồi thu thập các trajectory thành công làm dữ liệu SFT (Supervised Fine-Tuning).

2. Luồng 1: Khám Phá Website — Thuật Toán Go-Browse

2.1 Cấu Trúc Dữ Liệu Lõi (Core Data Model)

Đây là phần quan trọng nhất để hiểu framework. Mọi thứ đều xoay quanh một đồ thị có hướng biểu diễn website. Hãy liên hệ: Graph = đồ thị, Node = đỉnh, Trace = cạnh có trọng số (đường đi), Task = bài toán cần giải trên đỉnh đó.

webexp/explore/core/graph.py Graph

📥 Input
  • root_url: str — URL gốc để bắt đầu duyệt
  • exp_dir: str — thư mục lưu trữ kết quả
  • allowlist_patterns: Sequence[str] — regex cho phép
  • denylist_patterns: Sequence[str] — regex chặn
  • resume: bool — có tiếp tục từ lần chạy trước không
📤 Output / State
  • nodes: dict[str, Node] — ánh xạ URL → Node
  • explored_nodes: list[Node] — các đỉnh đã duyệt
  • unexplored_nodes: list[Node] — hàng đợi BFS
  • root: Node — đỉnh gốc
🧠 Logic & Liên Hệ Thuật Toán

Graph chính là một đồ thị có hướng biểu diễn website, cài đặt bằng danh sách kề (adjacency list): mỗi Node lưu danh sách children (các URL con). Việc duyệt đồ thị dùng chiến lược BFS: unexplored_nodes là hàng đợi FIFO, get_next_node() luôn lấy phần tử đầu tiên.

Hàm add_url() giống như thêm một đỉnh mới vào đồ thị — nếu URL đã tồn tại (visited) thì không thêm lại, tương tự như visited set trong BFS/DFS. Hàm check_if_url_allowed() dùng regex để lọc các URL được phép — giống như điều kiện ràng buộc trong tìm kiếm có giới hạn.

BFS Adjacency List Factory (load static method)

webexp/explore/core/node.py Node

📥 Input
  • url: str
  • tasks: dict[str, Task] — task đã xác minh khả thi
  • exploration_tasks: dict[str, Task] — task thô từ explorer
  • children: list[str] — URL con (cạnh ra)
  • description: str
  • prefixes: list[Trace] — đường đi từ trang khác đến node này
  • visited: bool
📤 Key Methods
  • add_task(goal) → Task — thêm task vào node
  • add_exploration_task(goal) → Task
  • add_trajectory(traj) — lưu trajectory vào task phù hợp
  • get_feasible_tasks() → list[Task] — lọc task có ít nhất 1 positive trajectory
  • update_save() — persist xuống disk
🧠 Logic

Mỗi Node là một trang web cụ thể. Nó chứa 2 loại task: tasks (đã kiểm tra khả thi) và exploration_tasks (task thô do explorer đề xuất). prefixes là danh sách Trace — mỗi trace ghi lại đường đi từ một URL khác đến node này. Đây là cơ chế định tuyến (routing): khi solver cần đến node này từ root, nó có thể dùng prefix làm "đường đi mẫu".

@dataclass Graph Vertex

webexp/explore/core/task.py Task

📥 Input
  • goal: str — mô tả nhiệm vụ (vd: "[MOD] Add iPhone 13 to cart")
  • positive_trajs: list[Trajectory] — trajectory thành công
  • negative_trajs: list[Trajectory] — trajectory thất bại
  • exp_dir: str
📤 Key Methods
  • is_feasible() → bool — có ít nhất 1 positive trajectory
  • add_trajectory(traj) — phân loại vào positive/negative
  • process_raw_goal(goal) → (str, list[str]) — tách tag [INFO]/[NAV]/[MOD]
🧠 Logic

Task là một bài toán cụ thể trên một trang web. Mỗi task chứa nhiều trajectory — cả thành công lẫn thất bại. Tag [INFO] (tìm kiếm thông tin), [NAV] (điều hướng), [MOD] (chỉnh sửa nội dung) được parse tự động bởi regex.

@dataclass Binary Classification (feasible/not)

webexp/explore/core/trajectory.py Trajectory & TrajectoryStep

📥 TrajectoryStep Input
  • action: str — hành động (vd: "click('42')")
  • parsed_action: str — hành động đã parse
  • thought: str — suy nghĩ của agent
  • observation: dict — screenshot + axtree + open_pages_urls
📤 Trajectory Output
  • steps: list[TrajectoryStep]
  • final_state: TrajectoryStep
  • goal: str, reward: float, success: bool
  • response: str — câu trả lời cuối cùng của agent
  • agent_info: dict — config của agent đã dùng
🧠 Logic

Trajectory là một chuỗi các bước (steps) mà agent thực hiện để hoàn thành một goal. Mỗi TrajectoryStep ghi lại: action (hành động), thought (lý do), và observation (trạng thái trang web sau hành động). Đây chính là đơn vị dữ liệu cơ bản dùng để huấn luyện: prompt = các observation + thought trước đó, completion = thought + action hiện tại.

@dataclass Sequence / Path in State Space

webexp/explore/core/trace.py Trace

📥 Input
  • steps: list[TrajectoryStep]
  • start_url: str — URL xuất phát
  • end_url: str — URL đích
📤 Purpose
  • Lưu đường đi ngắn từ A → B
  • Dùng làm prefix cho solver khi cần navigate đến node
  • Nhẹ hơn Trajectory (không lưu ảnh)
🧠 Logic

Trace là phiên bản rút gọn của Trajectory, chỉ lưu đường đi giữa 2 URL. Đây chính là cạnh có trọng số trong đồ thị — trọng số là chuỗi hành động cần thực hiện. Khi Graph mở rộng, mỗi node mới được lưu kèm prefixes là danh sách Trace chỉ đường đến nó.

Weighted Edge / Path

webexp/explore/core/evaluator.py Evaluator

📥 Input
  • trajectory: Trajectory
  • model_name: str (default: gpt-4o)
📤 Output
  • Gán trajectory.success = True/False
  • Gán trajectory.reward = 1.0/0.0
  • Lưu evaluation info vào trajectory.misc
🧠 Logic

Dùng GPT-4V (vision) để đánh giá trajectory: gửi ảnh chụp màn hình cuối cùng + action history + goal, hỏi model "success" hay "failure". Đây là cơ chế tự động đánh giá không cần ground truth — rất quan trọng vì đây là unsupervised data collection.

2.2 Thuật Toán Go-Browse — Duyệt Đồ Thị BFS Có Hướng Dẫn Bởi LLM

┌──────────────────────────────────────────────────────────────────────┐
│                    GO-BROWSE ALGORITHM (web_explore.py)              │
│                                                                      │
│  Input: root_url, allowlist, denylist, agent configs                │
│                                                                      │

│  2. WHILE unexplored_nodes not empty AND count < max_nodes:         │
│     │                                                                │
│     │  curr_node = graph.get_next_node()   ←── FIFO (BFS order)     │
│     │                                                                │

│     │  ║  │                 │  │                 │           ║     │

│     │  ║  │ xuất INFO/MOD/  │  │ [NAV] tasks     │           ║     │
│     │  ║  │ NAV tasks       │  │                 │           ║     │
│     │  ║  └────────┬────────┘  └────────┬────────┘           ║     │
│     │  ║           ↓                    ↓                     ║     │
│     │  ║     run_episode()       run_episode()                ║     │
│     │  ║     (agent tự do        (agent click link,           ║     │

│     │  ╚══════════════════════════════════════════════════════╝     │
│     │                                                                │
│     │  ╔══════════════════════════════════════════════════════╗     │

│     │  ║    giá → nếu success → task FEASIBLE                ║     │
│     │  ║    Giới hạn: max_feasible_page_tasks_per_node,      ║     │
│     │  ║              max_feasible_nav_tasks_per_node         ║     │
│     │  ╚══════════════════════════════════════════════════════╝     │
│     │                                                                │

│     │  ║  Với mỗi feasible task:                             ║     │
│     │  ║    • Có prefix (từ curr_node): num_trajs lần        ║     │
│     │  ║    • Không prefix (từ root): num_trajs lần          ║     │

│  Output: Graph với tasks + trajectories → lưu disk (JSON + PNG)     │

💡 Liên hệ thuật toán: Đây là BFS trên đồ thị web với mỗi bước được tăng cường bởi LLM. Thay vì chỉ duyệt URL, thuật toán còn "hiểu" nội dung trang để đề xuất task và đánh giá khả thi. unexplored_nodes là hàng đợi BFS, nhưng có thể mở rộng thành priority queue (TODO trong code) để ưu tiên các node "quan trọng" hơn — giống như Best-First Search.
⚠️ Tại sao dùng BFS thay vì DFS? BFS khám phá theo chiều rộng: các trang gần root được duyệt trước. Điều này phù hợp với web vì các trang "nông" (gần homepage) thường quan trọng hơn, và việc lan tỏa từ từ giúp thu thập task đa dạng hơn.

2.3 Hệ Thống Agent

webexp/agents/base_agent.py AgentFactory & Protocol Hierarchy

🧠 Design Pattern: Factory + Protocol/Interface

AgentFactory dùng Factory Pattern với registry toàn cục AGENT_FACTORY_REGISTRY. Các agent class được đăng ký qua decorator @AgentFactory.register. Khi cần tạo agent từ config YAML, chỉ cần gọi AgentFactory.create_agent(name=..., model_id=...).

Protocol hierarchy (Structural Typing — giống Interface trong Java/C#): 

Agent (Protocol)           ← get_action(), reset(), obs_preprocessor()
  ├── ExplorerAgent        ← get_proposed_tasks(), goal_str
  └── AgentWithExplorationCallbacks  ← pre/post step callbacks

BaseAgent (ABC)            ← implement cụ thể
  └── SolverAgent          ← @AgentFactory.register
        ├── PageExplorerAgent   ← @AgentFactory.register
        └── NavExplorerAgent    ← @AgentFactory.register

Factory Pattern Protocol (Structural Interface) Decorator (@register) Template Method (BaseAgent)

webexp/agents/solver_agent.py SolverAgent

📥 Input (per step)
  • obs: dict — observation từ BrowserGym (screenshot, axtree, DOM, URL...)
  • oracle_action: tuple[str,str] — hành động có sẵn (callback inject)
📤 Output (per step)
  • action: str — hành động cho BrowserGym (vd: "click('42')")
  • extras: dict — thought, parsed_action, model_usage
🧠 Logic

SolverAgent là agent chính để giải quyết task. Mỗi bước:

  1. obs_preprocessor: Chuẩn hóa observation — flatten axtree, prune HTML, extract URLs
  2. Prompt Builder: Xây dựng messages gồm system prompt + goal + axtree + action history + error context
  3. LLM Call (với adaptive retry): Gọi OpenAI-compatible API để sinh JSON {"thought": ..., "action": ...}
  4. extract_action_and_thought: Parse JSON từ raw output, xử lý edge case (text trước JSON, truncated JSON, zero-width chars)
  5. Stuck Detection: Phát hiện agent bị kẹt (cùng action lặp ≥6 lần, hoặc cùng action+error ≥3 lần)
  6. action_processor: Convert sang Python code cho BrowserGym

State Machine (per-step cycle) Cycle Detection (stuck detection)

webexp/agents/page_explorer_agent.py PageExplorerAgent

📥 Input
  • Kế thừa SolverAgent + thêm add_tasks_to_dataset() action
  • goal_str: "thu thập task [INFO]/[NAV]/[MOD] từ trang hiện tại"
📤 Output
  • get_proposed_tasks() → list[str] — danh sách task đã đề xuất
  • Mỗi task có tag: [INFO] information seeking, [NAV] navigation, [MOD] content modification
🧠 Logic

Agent này tự do khám phá trang web: click vào buttons, menus, hover elements để hiểu nội dung. Khi tìm thấy task khả thi, agent gọi add_tasks_to_dataset() — đây là một custom BrowserGym action được đăng ký vào HighLevelActionSet. Các task được tích vào TASK_COLLECTOR global list.

Quy trình khám phá: Tìm INFO tasks (dựa trên nội dung tĩnh) → NAV tasks (click link, go_back) → MOD tasks (tương tác form).

webexp/agents/nav_explorer_agent.py NavExplorerAgent

📥 Input
  • Giống PageExplorer nhưng goal_str tập trung vào NAV tasks
  • Callback: backtrack_when_new_page_found tự động go_back khi đến URL mới
📤 Output
  • get_proposed_tasks() → list[str] — chỉ [NAV] tasks
🧠 Logic

Khác với PageExplorer, NavExplorer được phép click link để đến trang mới, nhưng sau đó phải go_back về trang gốc. Callback backtrack_when_new_page_found tự động phát hiện khi URL thay đổi và inject oracle_action ("go_back()", ...) để agent quay về.

2.4 Cơ Chế Callback & Design Patterns

webexp/explore/core/agent.py wrap_agent_for_callback_protocol

🧠 Design Pattern: Decorator + Chain of Responsibility

Đây là một trong những pattern hay nhất trong framework. Agent được wrap bởi CallbackProtocolAgentWrapper — một dynamic class kế thừa ngay type của agent gốc. Wrapper này thêm pre-step và post-step callbacks được gọi trước và sau mỗi action.

Callback chain trong Go-Browse:

PRE-STEP:
  prestep_store_url           → lưu URL hiện tại vào callback_context

POST-STEP (theo thứ tự):
  backtrack_if_needed         → nếu URL bị block → go_back()
  process_open_urls_callback  → phát hiện URL mới → thêm node vào graph
  backtrack_when_new_page_found → (chỉ NavExplorer) nếu URL thay đổi → go_back()

Decorator Pattern Chain of Responsibility Observer Pattern Dynamic Proxy (Python __getattr__)

webexp/explore/core/episode.py run_episode()

📥 Input
  • goal: str — nhiệm vụ cần thực hiện
  • node: Node — node xuất phát
  • env: BrowserEnv — môi trường browser
  • agent: AgentWithExplorationCallbacks
  • evaluator: Evaluator
  • graph: Graph
  • max_steps: int
📤 Output
  • Trajectory — đầy đủ steps + final_state + response
  • Trajectory đã được evaluator đánh giá (nếu là solver)
🧠 Logic — Vòng Lặp Chính Của Một Episode
1. reset_env_to_node()    → mở browser, goto(node.url), set goal
2. agent.reset()          → xóa history
3. Trajectory.from_goal() → tạo trajectory rỗng
4. WHILE not done AND num_steps < max_steps:
   a. agent.run_pre_step_callbacks()    ← Chain of Responsibility
   b. agent.get_action(obs)             ← LLM inference
   c. env.step(action)                  ← thực thi trong browser
   d. agent.run_post_step_callbacks()   ← Chain of Responsibility
   e. Check has_new_assistant_message() → agent trả lời user?
      Nếu có: evaluator.evaluate(traj)  ← GPT-4V đánh giá
5. traj.extract_response(env)           ← lấy final message
6. Lưu final_state

└──────────────────────────────────────────────────────────────────┘
📥 Input Schema (raw)
  • traj_reward: float — 1.0 (thành công) / 0.0 (thất bại)
  • step_data: dict | list — chứa prompt + completion
  • step_data.prompt: list[dict] — messages hệ thống + user
  • step_data.completion: list[dict] — messages assistant
  • Mỗi message: {"role": "...", "content": "..."}
📤 Output Schema (processed)
  • messages: list[dict] — prompt + completion đã gộp
  • Mỗi message: {"role": "system/user/assistant", "content": "..."}
  • Định dạng chuẩn cho HuggingFace chat template
🧠 Logic — Tại Sao Không Apply Chat Template Ở Đây?

Chat template phụ thuộc vào tokenizer của model cụ thể. Ví dụ Qwen dùng <|im_start|>user\n...<|im_end|> trong khi Llama dùng format khác. Nếu apply chat template ở preprocess, khi đổi model phải chạy lại toàn bộ pipeline. Thay vào đó, preprocess chỉ gộp messages, còn training script mới apply chat template với đúng tokenizer của model đang train. Đây là separation of concerns.

Data Format Chi Tiết

Training-ready (sau apply_chat_template) {text: "<|im_start|>system\n...<|im_end|>\n<|im_start|>user\n..."} Chuỗi văn bản đã format theo chat template của model
🧠 Logic — Input & Target Cho Fine-Tuning

Đây là Supervised Fine-Tuning (SFT) với completion-only loss:

  • Input (prompt tokens): System prompt + Goal + Axtree (cây accessibility) + Action history + Error context
    → Loss = 0 (không học từ input)
  • Target (completion tokens): Thought + Action của assistant
    → Loss = cross-entropy (học cách sinh ra thought và action đúng)

DataCollatorForCompletionOnlyLM nhận diện phần assistant bằng response template (vd: <|im_start|>assistant\n) và chỉ tính loss trên các token sau mốc đó.

🔑 Insight quan trọng nhất: Go-Browse biến bài toán "thu thập dữ liệu huấn luyện web agent" thành bài toán "duyệt đồ thị có hướng dẫn bởi LLM". Mỗi node là một trang web, mỗi edge là một navigation path. LLM vừa đóng vai trò node expander (đề xuất task), feasibility filter (kiểm tra khả thi), và path sampler (tạo trajectory đa dạng). Kết quả là một tập dữ liệu SFT chất lượng cao mà không cần bất kỳ annotation thủ công nào.
